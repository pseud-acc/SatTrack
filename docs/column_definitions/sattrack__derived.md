Part of the SatTrack column definitions; see `00_overview.md` for the rules and decisions.

## Batch 8: SatTrack-derived columns (intermediate and marts)

Source: SatTrack-derived. Each row names the model or macro that computes it; the publishers of its inputs are cited in the definition.

There's no external publisher for these. Each definition **cites the model or macro that computes it, and the decision that set the rule** (the field review is `~/.claude/plans/sattrack-field-review.md`; the plan is `~/.claude/plans/sattrack-dbt-migration.md`). Each doc block carries a **"SatTrack-derived"** label. Where a rule combines sources, the precedence is spelled out so the definition can be tested. **Corrected 2026-11-08 against the current SQL**; the load metadata and audit rows (#27–#29) moved to `sattrack__metadata.md` (batch 8b).

**v3 placeholders dropped:** `source_priority` (the constant `'v3_python_extract_sql_transform'`) and `record_quality_score` (always NULL) carry no information. They're replaced by the per-field `*_source` lineage columns.

| 24 | `<date>`, `<date>_start`, `<date>_end`, `<date>_precision` | macros `helper__parse_vague_date_columns` (`_base`, `_start`, `_end`, `_precision`, `_unit`) | Parses a GCAT **Vague Date**, which "defines a time range within which an event is believed to lie" (https://planet4589.org/space/gcat/web/intro/vague.html). A trailing `?` is the "optional trailing question mark to indicate uncertainty"; GCAT's table shows it widening the range by one unit of the precision on each side (`2016 Jun?` = 2016 May 1 to 2016 Aug 1; `2016?` = 2015 Jan 1 to 2018 Jan 1). `<date>` = the date as written, as a timestamp, with the `?` and a trailing `s` ("scheduled date") ignored (`2016 Jun?` = 2016-06-01). `<date>_start` = start of the GCAT interval: the date as written, less one unit of the precision when the value ends in `?`. `<date>_end` = end of the interval: the date as written plus one unit, or plus two units when the value ends in `?` (so an uncertain range is three units wide). One unit is a second, minute, hour, day, month, quarter (3 months), year, decade (10 years), century (100 years) or millennium (1,000 years), or a centiday: 0.01 day for a two-digit day fraction (`2016 Jun 8.98`) and 0.1 day for a one-digit fraction (`2016 Jun 8.9`), as in GCAT's table. A century or millennium is written as an integer and a letter: GCAT: "20C means between 1901 Jan 1 and 2001 Jan 1" and "3M means between 2001 Jan 1 and 3001 Jan 1"; so `21C` = 2001-01-01 (`_start` 2001-01-01, `_end` 2101-01-01) and `21C?` = 2001-01-01 (`_start` 1901-01-01, `_end` 2201-01-01), by the same two rules as above. `<date>_precision` = `second`, `minute`, `hour`, `centiday`, `day`, `month`, `quarter`, `year`, `decade`, `century` or `millennium`, with `?` appended for GCAT's "uncertainty" flag; `current` for `*` (GCAT: "Now (for an end date, indicating still active)"); `unknown` for `?` alone ("Date entirely unknown"); `unparsed` for any other form (e.g. a year of fewer than four digits such as `843`). All dates are NULL for `*`, `?` and unparsed values. | **Decided 2026-10-25: `<date>` holds the interval start. Compared with the live DB built 2026-11-03 (date as written, no widening) no main column differs. `<date>_start` is carried to a mart only where its `<date>_end` is: `dim__org` (`org_start_date`, `org_stop_date`), `dim__launch_site` (`site_start_date`) and `fct__launch_event` (`launch_datetime`); the master has only `end_operation_date`, `end_transmission_date`, `launch_datetime` and their `_precision`.
